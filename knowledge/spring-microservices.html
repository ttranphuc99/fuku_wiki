// WK1-S01 — Spring Boot vs Spring Cloud

Boot vs Cloud — what each layer solves

one builds the service, the other coordinates a fleet of them

Spring Boot makes a single service easy: auto-configuration, embedded server, starters, opinionated defaults, production actuators (health, metrics). It answers "how do I ship one runnable app fast?"

Spring Cloud sits on top and solves the problems that only appear once you have many services talking to each other:

ConcernSpring Cloud piece
ConfigConfig Server — externalized, versioned config
DiscoveryEureka / Consul — find service instances dynamically
GatewaySpring Cloud Gateway — routing, auth, rate-limit at the edge
ResilienceResilience4j — circuit breaker, retry, bulkhead
TracingMicrometer / Sleuth → distributed traces

The honest caveat: a lot of what Spring Cloud once owned is now handled by the platform — Kubernetes does discovery (DNS/Services), config (ConfigMaps/Secrets), and a service mesh (Istio/Linkerd) can do retries and circuit breaking. Say that; it shows you know where the industry moved.

Q: Do you still need Spring Cloud on Kubernetes?
A: Less of it. K8s covers discovery and config; a mesh covers traffic resilience. I'd still use Boot for the app and Resilience4j for app-level fallbacks, but I wouldn't reflexively add Eureka/Config Server if the platform already provides those primitives.

REST vs gRPC vs Async Messaging

and when you'd pick each in a payment flow
REST/JSONgRPCAsync (Kafka/Rabbit)
Stylerequest/responserequest/responsefire-and-forget / events
Couplingtemporal (both up)temporal (both up)decoupled in time
Perfgoodbest (HTTP/2, protobuf, streaming)high throughput
Best forpublic/partner APIsinternal service-to-serviceevents, buffering, decoupling

In a payment flow, mix them deliberately:

  • Synchronous where the caller must know the result now — the merchant needs an auth decision before showing "approved". REST at the edge, maybe gRPC internally to the risk/auth services.
  • Asynchronous for everything that can happen after — emit a PaymentAuthorized event; ledger posting, notifications, analytics, and settlement all consume it. This buffers spikes and decouples the slow parts from the hot path.

Kafka vs RabbitMQ: Kafka = durable, replayable log, high throughput, great for event streaming and audit trails (payments love replay for reconciliation). RabbitMQ = flexible routing, per-message ack, good for classic task queues. For a payments event backbone, Kafka's ordered, retained log is usually the better fit.

Q: Why not make the whole payment flow synchronous?
A: Every synchronous hop couples availability — if settlement is down, you can't authorize. Keeping the hot path (auth) sync and pushing the rest onto an event log means a downstream outage degrades gracefully instead of failing the customer's payment.
// WK1-S03 — resilience patterns

Resilience Patterns

a stuck downstream call is how one dependency takes down the whole gateway
PatternProblem it solves
TimeoutNever wait forever. A hung call holds a thread; enough of them exhaust the pool.
Retry + backoffRide out transient blips — with exponential backoff + jitter so you don't stampede a recovering service. Only retry idempotent ops.
Circuit BreakerAfter N failures, "open" and fail fast for a cooldown, then "half-open" to test recovery. Stops cascading waits.
BulkheadIsolate resources per dependency (separate thread pools / connection limits) so one slow partner can't drown the others.
FallbackGraceful degradation — cached response, queue-for-later, or a clear decline instead of a hang.
Rate limitProtect yourself and downstreams from overload / abuse.
// Resilience4j — annotations compose @CircuitBreaker(name = "acquirer", fallbackMethod = "queueForRetry") @Retry(name = "acquirer") // exp backoff + jitter @Bulkhead(name = "acquirer") // isolate this partner @TimeLimiter(name = "acquirer") public CompletableFuture<Auth> authorize(Charge c) { ... }

Critical nuance for payments: retry is dangerous without idempotency. If you retry a charge that actually succeeded but whose response was lost, you double-charge. Every retryable payment operation must carry an idempotency key so the server dedupes. (See the Payments Vocabulary page.)

Q: A downstream bank API starts responding in 30s instead of 200ms. What protects you?
A: A tight timeout caps the wait; a bulkhead keeps those slow calls off the threads serving other partners; the circuit breaker trips after repeated timeouts so we fail fast and shed load; a fallback queues the request for retry. Together they contain the blast radius to that one partner.

⚡ Interview Talking Points

01
Distinguish Boot from Cloud crisply: "Boot makes one service productive; Cloud coordinates many. On Kubernetes I let the platform own discovery and config, and keep app-level resilience in Resilience4j."
02
Justify sync vs async by coupling: "I keep the authorization hot path synchronous because the merchant needs an answer, and push ledger, notifications and settlement onto an event log so a downstream outage degrades gracefully instead of failing the payment."
03
Always pair retry with idempotency: "Retries are only safe if the operation is idempotent — in payments that means an idempotency key the server dedupes on, otherwise a retried-but-actually-succeeded charge double-charges."
04
Tell the cascade story: "One slow dependency exhausts the thread pool and takes down endpoints that don't even use it. Timeout + bulkhead + circuit breaker exist to contain that blast radius."
