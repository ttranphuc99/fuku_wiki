Design a Ledger & Reconciliation System

// guarantee no double-charge or lost transaction across failures

// 1 — the core: an append-only double-entry ledger

Ledger design

Model money as an immutable, append-only log of balanced entries. Every transaction posts equal debits and credits across accounts; the sum is always zero. You never update or delete a posting — a correction is a new reversing entry. That immutability is what makes the ledger auditable and safe to rebuild.

Entry: txn_id, account, direction(DR/CR), amount, currency, ts Invariant: sum(debits) == sum(credits) per txn_id Balance: derived = fold over entries (or a maintained snapshot)
  • Idempotency: a unique constraint on (txn_id) (or idempotency key) makes re-posting a no-op — the anti-double-charge guarantee lives here.
  • Atomic multi-leg write: all legs of one transaction commit in a single DB transaction, or none do.
  • Balances: derive by folding entries for correctness; keep a maintained running-balance snapshot for read performance, rebuildable from the log.
// 2 — durability: don't lose a transaction
  • Write-ahead / commit the intent first: persist the transaction request durably before doing side effects, so a crash can resume.
  • Outbox pattern: ledger write + outbound event in one transaction; a relay publishes to Kafka. Guarantees the event and the posting never diverge.
  • At-least-once delivery + idempotent consumers = effectively exactly-once. Duplicates are harmless because the unique constraint absorbs them.
  • Event sourcing angle: the ledger is the event log; current balances are a projection you can always recompute.

Exactly-once is a myth on the wire — you get at-least-once delivery and make processing idempotent. Say that explicitly; it signals maturity.

// 3 — reconciliation as a safety net

Reconciliation compares the internal ledger against external truth — bank/network settlement files, PSP reports — on a schedule (often nightly batch + intraday). It detects divergence; it is not the primary correctness mechanism.

Load external settlement file ┐ Match by reference/amount/date ┤ → 3-way: internal ⇄ acquirer ⇄ bank Classify unmatched ┘
Break typeMeaning & action
Missing internalBank has it, we don't — investigate lost txn; post correcting entry.
Missing externalWe have it, bank doesn't yet — timing (in-flight) or a failed settlement.
Amount mismatchFees, FX, or a bug — route to ops queue.
DuplicateIdempotency failure upstream — should be rare if constraints hold.

Unmatched items flow to an exceptions queue for automated rules + human review. Track a reconciliation-break metric; a rising trend is an early warning of an upstream bug.

// 4 — trade-offs to state
ConsistencyStrong within a ledger partition (ACID); the money invariant can't be eventual.
PartitioningShard by account to scale, but keep both legs of a transfer resolvable atomically (or use a saga for cross-shard with compensation).
Correctness netIdempotency + immutability = primary guarantee; reconciliation = detection net.

⚡ Interview Talking Points

01
Immutability first: "The ledger is append-only double-entry — corrections are reversing entries, never updates. That's what makes it auditable and rebuildable."
02
Locate the anti-double-charge guarantee precisely: "The no-double-charge property comes from a unique constraint on the transaction/idempotency key plus an atomic multi-leg write — not from reconciliation."
03
Be honest about exactly-once: "There's no exactly-once on the network — I use at-least-once delivery with idempotent consumers, so duplicates are absorbed harmlessly."
04
Frame reconciliation correctly: "Reconciliation against settlement files is a detection safety net that catches divergence early — it's not the primary correctness guarantee, and treating it as one is a red flag."
