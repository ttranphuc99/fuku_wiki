// WK1-J01 — concurrency fundamentals

Concurrency

synchronized vs Lock · thread pools · CompletableFuture · race conditions

The mental model: a race condition happens when two threads touch shared, mutable state and at least one writes, with no ordering guarantee between them. You fix it by removing sharing, removing mutation, or adding coordination.

synchronized vs Lock (ReentrantLock). Both give mutual exclusion + visibility. Reach for Lock when you need what synchronized can't do:

  • tryLock / timed lock — back off instead of blocking forever (deadlock avoidance)
  • interruptible acquisition — cancel a thread waiting on a lock
  • fairness policy, and multiple Conditions per lock (e.g. notFull / notEmpty)
  • ReadWriteLock — many readers, one writer, for read-heavy state

synchronized is simpler, JIT-optimized (biased/lightweight locking), and auto-releases on exception. Default to it; upgrade to Lock only for the features above.

Thread pools (ExecutorService). Never new Thread() per task in a service. Size pools by workload:

WorkloadSizing rule
CPU-bound~ #cores (+1)
IO-boundhigher — cores × (1 + wait/compute)
Isolationseparate pools per dependency (bulkhead)

Prefer a bounded queue + explicit RejectedExecutionHandler — an unbounded queue turns backpressure into an OOM.

CompletableFuture — compose async work without blocking threads:

// fan-out two calls, combine, with a timeout + fallback CompletableFuture<Risk> risk = supplyAsync(() -> riskClient.score(req), pool); CompletableFuture<Limit> limit = supplyAsync(() -> limitClient.get(req), pool); risk.thenCombine(limit, (r, l) -> decide(r, l)) .orTimeout(300, MILLIS) .exceptionally(ex -> Decision.reviewLater());

Key gotchas: thenApply (sync, same thread) vs thenApplyAsync (handed to a pool); always pass your executor, never rely on the common ForkJoinPool for blocking IO.

Modern concurrency utilities to name-drop: AtomicLong/LongAdder (lock-free counters), ConcurrentHashMap, BlockingQueue (producer/consumer), CountDownLatch/CyclicBarrier, and virtual threads (Project Loom, Java 21) — cheap threads that make the thread-per-request model viable again for IO-bound services.

Q: How do you make a class thread-safe?
A: In priority order — (1) make it immutable (final fields, no setters); (2) confine state to one thread; (3) use concurrent collections / atomics; (4) only then reach for explicit locks, holding them for the shortest critical section possible.

JVM Memory & GC

reason about trade-offs — you don't need to tune flags live

Memory regions: the heap (young gen = Eden + survivors, old gen) holds objects; metaspace holds class metadata (native memory, not heap); each thread has a stack. Most objects die young — that's the assumption every collector exploits (generational hypothesis).

How GC works: mark reachable objects from GC roots, sweep/compact the rest. A young (minor) GC is cheap and frequent; a full/old GC is expensive. The whole game is minimizing pause time and frequency while keeping throughput.

CollectorOptimizes forUse when
G1 (default)balanced, predictable pausesmost services; heaps up to ~tens of GB
ZGCultra-low pause (<1ms), huge heapslatency-critical, large heap (payments!)
Shenandoahlow pause, concurrent compactionsimilar niche to ZGC
Parallelraw throughput, pauses OKbatch / offline jobs

The trade-off in one sentence: low-pause collectors (ZGC/Shenandoah) do more work concurrently with your app, spending CPU and a bit of throughput to avoid stop-the-world pauses — exactly the deal you want for a payment API with a p99 latency SLA.

  • Memory leak in Java: objects still reachable but never used — static collections that only grow, unbounded caches, unclosed resources, listeners never deregistered.
  • OOM causes: heap too small, a leak, or genuinely too much live data. Capture a heap dump (-XX:+HeapDumpOnOutOfMemoryError) and read it, don't just bump -Xmx.
  • Stop-the-world: phases where all app threads pause. Long STW = latency spikes = failed payments. This is why collector choice matters.
Q: Your service has p99 latency spikes every few minutes. First hypothesis?
A: GC pauses. Check GC logs for full-GC frequency/duration correlated with the spikes. Fixes: right-size the heap, move to a low-pause collector (ZGC), or reduce allocation rate / a leak that keeps triggering old-gen collection.

SOLID & Patterns for Payments

principles you defend + the 5 patterns that actually show up in payment code

SOLID, one line each:

  • Single Responsibility — one reason to change per class
  • Open/Closed — extend without editing (new payment method = new Strategy, not a new if)
  • Liskov — subtypes must honor the base contract
  • Interface Segregation — many small interfaces > one fat one
  • Dependency Inversion — depend on abstractions; inject the concrete
PatternIn payments
StrategyPluggable payment methods / acquirers / fee rules — pick behavior at runtime, no giant switch.
Chain of ResponsibilityA processing pipeline: validate → fraud → auth → ledger. Each handler passes or rejects.
Circuit BreakerStop hammering a failing bank/partner; fail fast, recover automatically.
SagaLong-running distributed transaction as a sequence of local txns + compensations (no 2PC).
Idempotent ConsumerDedup by idempotency key so a retried/redelivered message charges exactly once.
// Strategy — Open/Closed in action interface PaymentMethod { Result charge(Money amt, Context ctx); } class CardPayment implements PaymentMethod { ... } class VietQrPayment implements PaymentMethod { ... } // new method = new class. Existing code never changes.
Q: Where would you use Chain of Responsibility vs Strategy?
A: Strategy picks one interchangeable algorithm. Chain runs a sequence of handlers where any can short-circuit. A payment request flows through a chain (fraud, limits, auth); within the auth step, a Strategy selects which acquirer to call.

⚡ Interview Talking Points

01
Frame concurrency around state, not keywords: "Thread-safety is about shared mutable state. I remove sharing or mutation first — immutability and confinement — and only reach for locks when I genuinely must coordinate."
02
Show you reason about GC, not tune it: "For a payments API I care about tail latency, so I'd lean toward a low-pause collector like ZGC — it trades a little throughput and CPU to avoid stop-the-world pauses that would show up as failed transactions."
03
Tie patterns to real code: "Adding a new payment method shouldn't mean editing a switch statement — that's Open/Closed. I model methods as a Strategy and the processing steps as a Chain of Responsibility."
04
Name-drop Loom to sound current: "Virtual threads make the simple thread-per-request model viable again for IO-bound services — you get readable blocking code without exhausting OS threads."
