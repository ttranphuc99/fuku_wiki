Week 2 · System Design · WK2-D01

Design a Payment Gateway

// client → auth → risk → ledger → settlement, retry-safe & idempotent

// 1 — clarify requirements first (always)

Functional

  • Accept a charge, authorize, capture, refund
  • Multiple methods (card, VietQR, wallet)
  • Idempotent create + status query + webhooks
  • Immutable transaction history

Non-functional

  • Correctness > availability > latency — never double-charge or lose a txn
  • p99 auth < ~300ms; high availability
  • PCI-DSS; full auditability
  • Scale to peak (sale events, payday)

State the ranking out loud: in payments, consistency of money movement is non-negotiable; you'll trade latency and even some availability before you'll risk a double-charge.

// 2 — the request flow
Client → API Gateway (authN, rate-limit, TLS) → Payment Service (validate + idempotency check) → Risk/Fraud (sync score, latency-budgeted) → Acquirer/Bank (authorize) ─┐ → Ledger (append auth hold) │ same logical txn → emit PaymentAuthorized event ─┘ → async: capture, settlement, notify, analytics
  • Idempotency at the front door: every create carries an Idempotency-Key; store it with the result so retries replay, not re-charge.
  • State machine per payment: CREATED → AUTHORIZED → CAPTURED → SETTLED (or DECLINED / FAILED / REFUNDED). Persist transitions; they drive recovery.
  • Outbox pattern: write the ledger row and the "publish event" intent in one DB transaction, then a relay ships it to Kafka — so you never post to the ledger without emitting the event, or vice versa.
// 3 — key decisions & trade-offs
DecisionChoice & why
ConsistencyStrong for the ledger write (single-partition, ACID); eventual for downstream (settlement, notifications) via events.
Distributed txnSaga with compensations (release hold / reverse), not 2PC.
DeliveryAt-least-once + idempotent consumers = effectively exactly-once processing.
Data storeStrongly-consistent RDBMS for ledger/txn state; the ledger is append-only double-entry.
ResilienceTimeout + circuit breaker + bulkhead around each acquirer; fallback = queue for retry.
// 4 — failure modes & recovery
  • Lost response after a successful auth: idempotency key + persisted state machine → retry returns the existing result.
  • Acquirer timeout (unknown outcome): mark PENDING, reconcile against the network settlement file; never assume success or failure.
  • Crash mid-flow: recover from persisted state; outbox guarantees the event still ships.
  • Partner outage: circuit breaker opens, requests queue, auto-recover on half-open.
// 5 — rollout & observability

Ship it safely: feature flags, canary a small % of traffic, dark-launch the new path in shadow mode comparing against the old, and keep a fast rollback.

Alert on money-movement signals, not just CPU:

  • Authorization success rate drop (per acquirer/method)
  • Latency p99 breach on the auth path
  • Ledger vs settlement reconciliation mismatch count
  • Pending/unknown transactions aging past threshold
  • Circuit-breaker open events, DLQ depth

⚡ Interview Talking Points

01
Open by ranking non-functionals: "Before I draw anything — in a gateway, correctness of money movement beats availability beats latency. That ranking drives every choice I'm about to make."
02
Make idempotency + state machine the backbone: "The idempotency key plus a persisted payment state machine is what makes the whole thing retry-safe — a lost response never becomes a double-charge."
03
Use the outbox to sound production-hardened: "I write the ledger entry and the event-publish intent in one transaction via an outbox, so the ledger and the event stream can never diverge."
04
Name the unknown-outcome case: "The scary state isn't failure, it's unknown — an acquirer timeout. I mark it pending and let reconciliation resolve it; I never guess."
