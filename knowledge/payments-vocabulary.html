// WK1-P01 — ISO 8583 vs modern REST/JSON

ISO 8583 vs Modern Payment APIs

how cards talked for 40 years vs how gateways talk today

ISO 8583 is the legacy binary messaging standard behind card networks (ATMs, POS, Visa/Mastercard rails). Messages are a Message Type Indicator + a bitmap indicating which numbered data elements are present (DE2 = PAN, DE4 = amount, DE39 = response code…). Compact, fixed-ish, ubiquitous in banking — and painful: positional, poorly self-describing, many regional variants.

Modern gateways (Stripe, Adyen, local PSPs) expose REST/JSON over HTTPS: human-readable, versioned, webhook-driven, easy to integrate. Under the hood they still translate down to ISO 8583 / network-specific formats when they hit the card rails.

The one-liner: "ISO 8583 is the wire format at the network layer; REST/JSON is the developer-facing API. A gateway's job includes bridging the two."

// WK1-P02 — idempotency keys ★

Idempotency Keys

the single most-asked concept in payment gateway interviews

Problem: networks are unreliable. A client sends "charge $50", the charge succeeds, but the response is lost. The client retries. Without protection, you charge twice.

Solution: the client generates a unique idempotency key (e.g. a UUID) per logical operation and sends it on every retry. The server stores the key with the result. Same key again → return the stored result, don't re-execute.

// POST /charges Idempotency-Key: 7f3c...-uuid if (store.exists(key)) return store.get(key); // replay prior result Result r = executeCharge(req); // do it once store.put(key, r, 24h); // dedup window return r;
  • Store the key atomically with the charge (same DB txn) or use a unique constraint — otherwise two concurrent retries both slip through.
  • Bind the key to the request payload hash so the same key with a different amount is rejected, not silently replayed.
  • Give keys a TTL; keys are scoped per endpoint/merchant.

Idempotent vs at-least-once: message systems deliver at least once, so consumers must be idempotent — same "Idempotent Consumer" pattern applied to events.

// WK1-P03 — ledger, reconciliation, settlement vs clearing

Ledger · Reconciliation · Clearing vs Settlement

double-entry mechanics and what actually moves money

Double-entry ledger: every transaction is recorded as balanced debits and credits across accounts — the books always sum to zero. It's append-only (you never edit a posting; you post a reversing entry). This gives an auditable, tamper-evident history — the source of truth for balances.

  • Authorization — check & hold funds; no money moved yet.
  • Capture — commit the authorized amount.
  • Clearing — networks exchange transaction details and net out who owes whom.
  • Settlement — the actual movement of funds between banks (often T+1/T+2, batched).

Reconciliation = comparing your internal ledger against external statements (bank/network settlement files) to catch mismatches — missing, duplicated, or wrong-amount transactions. It's a safety net, run continuously, not the primary correctness guarantee.

Q: Clearing vs settlement in one breath?
A: Clearing is agreeing on what is owed (exchanging and netting transaction data); settlement is actually moving the money to discharge those obligations.
// WK1-P04 — PCI-DSS basics

PCI-DSS Basics

the security bar for anyone touching card data

PCI-DSS (Payment Card Industry Data Security Standard) governs how cardholder data is handled. The engineering-relevant essentials:

  • Never store the raw PAN (card number) if you can avoid it; never store CVV after authorization, ever.
  • Tokenization — replace the PAN with a meaningless token; the real number lives in a vault. Shrinks your PCI scope dramatically.
  • Encryption at rest and in transit (TLS everywhere).
  • Least privilege & segmentation — restrict who/what can reach the cardholder-data environment; log and monitor access.

Scope reduction is the game: the less card data flows through your systems (tokenization, hosted fields, redirect flows), the cheaper and safer your compliance.

// WK1-P05 — 2PC vs Saga ★

2PC vs Saga

distributed transactions — Saga is what real payment systems use
Two-Phase CommitSaga
Howcoordinator: prepare → commit across allsequence of local txns + compensations
Consistencystrong (ACID across services)eventual
Lockingholds locks until commit — blockingno global locks
Failurecoordinator is a SPOF; blocks on crashcompensate completed steps
Scalepoor under load / partitionsscales, availability-friendly

Saga in practice: a payment = reserve funds → charge → post ledger → notify. If a later step fails, run compensating actions for the completed ones (e.g. release the reservation, post a reversal). Two flavors: choreography (services react to each other's events — decoupled but harder to trace) and orchestration (a central orchestrator drives the steps — clearer, easier to reason about).

Q: Why not 2PC for payments?
A: 2PC holds locks and blocks on coordinator failure — unacceptable for a high-throughput, always-on payment system, and most modern datastores/queues don't support it well. Saga trades strong consistency for availability and uses compensations to reach a correct end state.
// WK1-P06 — Vietnam-specific context

Vietnam Fintech Context

local awareness a generic candidate won't have
NapasNational payment switch — operates the domestic 24/7 real-time interbank transfer network and card switching. The rails most local e-wallets/banks ride on.
VietQRStandardized QR code scheme (built on Napas) for account-to-account transfers & merchant payments — hugely popular, near-instant, low cost.
SBVState Bank of Vietnam — the central bank / regulator. Sets licensing, intermediary payment service rules, and increasingly data/e-wallet regulation.
e-KYCElectronic Know-Your-Customer — remote identity verification (ID + biometric/liveness). Enabled account opening & wallet onboarding without a branch visit.
WalletsMoMo, ZaloPay, VNPay — dominant e-wallets; VNPay/Payoo strong on merchant QR acquiring.

Talking point: "Vietnam skipped a lot of card infrastructure and went straight to QR + real-time A2A via Napas/VietQR — so a modern gateway here optimizes for instant bank transfers and wallet rails, not just card processing, and has to stay inside SBV's intermediary-payment licensing and e-KYC requirements."

⚡ Interview Talking Points

01
Lead every retry answer with idempotency: "In payments, safe retries require an idempotency key the server dedupes on — that's how you turn an unreliable network into exactly-once charging."
02
Show ledger discipline: "Balances live in an append-only double-entry ledger — you never mutate a posting, you post a reversal. Reconciliation against settlement files is the safety net, not the source of truth."
03
Default to Saga, and know why: "Real payment systems use Sagas with compensations, not 2PC — 2PC's locking and coordinator dependency don't survive high throughput or partitions."
04
Drop local knowledge: "Napas runs the 24/7 interbank rails, VietQR standardizes QR payments on top, and SBV is the regulator with e-KYC and intermediary-payment licensing — context a non-local candidate simply won't have."
