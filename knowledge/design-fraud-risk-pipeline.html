Fraud / Risk Scoring Pipeline

// sync vs async scoring and the latency-budget trade-off

// 1 — the central tension

Latency budget vs catch rate

Fraud scoring sits inside the authorization hot path, which has a tight latency budget (say ~300ms p99 total). The more signals and heavier the model, the better the catch rate — but the slower the decision. The design is fundamentally about splitting work between what must happen before you authorize and what can happen after.

SynchronousAsynchronous
Wheninline, before auth decisionafter auth, streaming / batch
Budgeta few tens of msseconds → minutes
Doesfast rules, cached features, light model → approve / decline / step-upheavy ML, graph analysis, cross-txn patterns → flag, hold, claw back
Goalblock obvious fraud, keep latencycatch sophisticated fraud, feed models
// 2 — the pipeline
Inline (sync, in auth path) txn → feature lookup (cache/feature store) → rules engine + light model → score → {approve | decline | step-up (3DS/OTP)} Offline (async, off the hot path) txn event → stream processor → heavy ML + graph/velocity features → risk flags, case management, model retraining
  • Feature store — precompute expensive features (user 30-day velocity, device history, merchant risk) offline; the sync path only does fast lookups, never heavy computation.
  • Rules + model hybrid: deterministic rules for known-bad + hard limits (explainable, instant), ML score for the grey zone.
  • Step-up instead of a binary allow/deny: when risk is medium, challenge (3-D Secure, OTP) rather than decline a good customer.
  • Stream processing (Kafka + Flink/Kafka Streams) for real-time velocity checks and near-real-time flags that don't need to block auth.
// 3 — key decisions
Timeout policyThe scorer has a hard budget. On timeout, fail toward a safe default — for high-value txns maybe step-up; for low-value, approve-and-review. Don't hang the payment.
ConsistencySync path reads a slightly stale feature store — acceptable; freshness comes from the async stream.
False positivesBlocking a legit customer has real business cost. Tune thresholds by segment; prefer step-up over decline.
Feedback loopChargeback / confirmed-fraud labels flow back to retrain models and update rules.
ExplainabilityDecisions may need to be justified (disputes, regulators) — keep reason codes, not just a black-box score.
// 4 — what to monitor
  • Scoring latency p99 vs budget; timeout/fallback rate
  • Approve / decline / step-up rates (sudden shifts = model or attack)
  • False-positive proxy (step-up abandonment) & fraud/chargeback rate
  • Feature store freshness / staleness lag

⚡ Interview Talking Points

01
Frame it as budget-splitting: "Fraud scoring is a latency-vs-catch-rate trade-off. I put fast rules and cached-feature lookups inline to block obvious fraud within budget, and push heavy ML and graph analysis to an async stream off the hot path."
02
Feature store is the trick: "The sync path can't compute a 30-day velocity in 20ms, so I precompute features offline and only do lookups inline. That's how you get rich signals without blowing the budget."
03
Step-up beats binary: "For medium risk I challenge with 3DS/OTP instead of declining — a false decline is lost revenue and an angry customer, so I design for step-up, not just allow/deny."
04
Have a timeout doctrine: "The scorer has a hard budget; on timeout I fail to a safe default keyed on transaction value — I never let risk scoring hang the authorization."
